# Independent Problem Analysis

The request asks that `harness/planner.py` (1) deterministically derive required inputs, (2) resolve schools safely, (3) normalize requested metrics, (4) construct exact evidence requests, and (5) surface planner-generated bad requests as failures rather than as unsupported user questions. Each verb sits on a boundary the contract and the ADRs already police: the split between REQUIRED and DEFAULTABLE inputs, between harness identity resolution and prohibited crosswalks, between a harness defect and an honest refusal, and between deterministic code and the model's judgement. The framing is coherent, but it is stated at a level of abstraction that lets several contract obligations be satisfied in letter while a harness defect is masked as a customer-facing `Unsupported`. Because the host did not return `planner.py` or its tests, I cannot confirm the current behaviour; the concerns below are framed as falsifiable claims with the observation that would settle each.

## Authority and requirement risks

- **"Derive required inputs" can silently expand into defaulting.** The contract states `request` is "exactly what the harness supplied" and `resolved_request` "contains all validated, defaulted and dynamically resolved values" (`POC_CONTRACT_V0.3_SPEC.md`; registry `common_response_rules`). Defaulting (year ranges, metric defaults, ERP/SEIFA selectors) is explicitly the data layer's job. A plausible plan that "derives required inputs" could start populating DEFAULTABLE fields in the outbound `request`, usurping the emitter's defaulting authority and changing the echoed `request`. Evidence this would be wrong: `golden_cases.json` answer cases deliberately omit defaultable inputs (e.g. `answer/VC-POC-01` expects only `acara_sml_id` + two metrics, note: "Omits every defaultable input ... so answering rather than asking is part of what this case grades"). Disproved if `planner.py` restricts derivation to registry `input_policy.required`/`material` and never writes `defaultable` keys into `request`.
- **Source-of-truth ambiguity for "required."** The same required/material/conditional_material policy is expressed in at least three vendored places — the registry `input_policy`, each `x-poc` block in the per-question request schema, and `_index.json` — plus the interim shim `settings.MATERIAL_INPUTS` (`decisions.md` O-1). "Deterministically derive" is only deterministic if one of these is authoritative. If the planner reads `settings.MATERIAL_INPUTS`, it inherits the O-8 defect (below). Disproved by showing the planner reads the pinned registry/schema, not the shim.
- **Stale-interim risk.** `decisions.md` (O-1, ADR-009 interim) still describes v0.2.0 shims to be deleted "when [v0.3.0] lands," yet `PINNED.json`, the registry and `golden_cases.json` are all `contract_version: 0.3.0`. This is a documentation/authority conflict: the plan could treat the v0.2.0 interim behaviour as current when the pinned contract is already v0.3.0. Disproved by evidence that the shims (`MATERIAL_INPUTS`, harness-side empty/partial detection) are already removed or that O-1 is closed.
- **"No arithmetic / faithful slot filler" boundary (ADR-001).** Normalizing metrics and constructing requests must not become deriving figures or inferring metrics the user did not ask for. `rules.md` step 2 warns "never add a metric merely because it is related or available." Disproved if metric normalization is a fixed synonym map (e.g. "teaching staff" → `teaching_fte`) with no expansion beyond the user's words.



## Missing constraints and failure modes

- **The load-bearing verb (5) is under-specified.** "Surface planner-generated bad requests as failures rather than unsupported user questions" requires distinguishing a `bad_request` the emitter returns because the *planner* mis-built the request (a harness defect) from a legitimate refusal/clarification. ADR-014 decision 1 shows the current path converts an unrepairable `bad_request` into `RepairCapExceeded` → an `Unsupported` carrying the data layer's message — i.e. exactly the conflation the request wants removed. A plan could satisfy the other four verbs and leave this masking intact. Disproved by a code path that raises an internal/failure outcome (not `Unsupported`) when the planner itself produced a schema-invalid request.
- **Zero-match vs multi-match vs absent-ID school resolution.** `rules.md` step 1 and the error boundary define distinct outcomes: multiple matches → clarify; an `acara_sml_id` absent from the pinned directory → `bad_request` (repairable); a directory-valid record lacking geography → `unanswerable`. "Resolve schools safely" must map each to the correct outcome and must never name-match across source systems or synthesize a `School_No`→`ACARA_SML_ID` crosswalk (registry `excluded_topics`; ADR-001). A plan could collapse zero-match into a generic `Unsupported`. Disproved by tests covering all three branches separately.
- **Conditional materiality of** `distance_km` **(O-8).** The registry makes `distance_km` material for VC-POC-05/06/07 *only when* `market_definition == distance`; `decisions.md` O-8 records that the gate currently treats it as unconditional and that this is pinned by a strict `xfail` in `tests/unit/test_agent_loop.py`, with an explicit instruction "do not build a second hand-maintained condition table." A planner that "deterministically derives required inputs" is precisely where a second condition table would be introduced, which would flip the `xfail` and fail the suite. Disproved if the planner derives conditional materiality from the schema/registry `conditional_material` rather than a new hardcoded table, and the O-8 entry is updated in lockstep.
- **String-parsed conditions (G-4).** `decisions.md` O-6/G-4 records that the conditional requirement is currently extracted by string-splitting the registry prose ("distance_km when market_definition is distance"). If the planner keeps that mechanism, rewording the registry silently changes behaviour. Disproved by structured reading of `conditional_material` keys.
- **VC-POC-09/10 "at least one explicit filter" (OD-07).** This is registry/emitter-enforced; the schemas express only `minProperties>=1`, and VC-POC-09 defaults `sectors` while the constraint demands a filter *beyond* the sector default. The golden `clarify/peer_filters` and `clarify/segment_filters` cases expect clarification, so the planner must not auto-satisfy these from defaults. Disproved by tests asserting clarification when only the sector default is present.



## Architecture and compatibility assumptions

- **Do not assume the O-8** `xfail` **is unaffected.** Any deterministic materiality derivation touches the exact behaviour that `test_agent_loop.py` pins; the plan must state whether it fixes or preserves O-8. Verify by locating the `xfail` and the planner's materiality source.
- **Do not assume** `request` **shape freedom.** Replay equality compares the whole successful response as semantic JSON minus `provenance.generated_utc` (registry `replay_equality`). If the planner reorders or over-populates request arrays, it may perturb `resolved_request`/evidence-filter agreement, which the contract requires ("evidence filters must agree with it"). Verify array-ordering determinism and request↔resolved_request agreement.
- **Do not assume metric normalization is free to move from prompt to code.** `rules.md` currently assigns the "teaching staff"→`teaching_fte` and headcount rules to the model. Moving them into the planner changes ownership and could diverge from the prompt (ADR-006/ADR-015 keep the prompt generated from the contract). Verify the golden `answer/`* expected requests still match after normalization, and that prompt and planner do not both — or neither — own the rule.
- **Do not assume the stub/live substrates agree.** `decisions.md` O-6 warns that `result.data` and directory record shapes are still invented in the stub; a planner change validated only offline (ADR-016's "nothing offline reaches a provider") proves nothing about live directory resolution. Verify whether planner behaviour depends on preflight fields the stub fabricates.
- **Contract pin (ADR-008).** A planner change must not touch `contract/`; `test_contract_pin.py` recomputes hashes. Verify the change is code-only.



## Acceptance hazards

- **The failure-vs-refusal distinction must be an assertable observable.** A contract test must exercise a planner-authored invalid request and assert the outcome is a harness *failure* (e.g. `internal`/typed exception), NOT an `Unsupported` rendered to the user — otherwise verb (5) is untested. Hazard: a test that only checks "an error is returned" passes both the correct and the masked behaviour.
- **Determinism must be tested at the planner boundary, not end-to-end.** Because the model still selects the question and extracts intent, overall pass^k reliability is not a planner determinism proof. A test should feed a fixed intent/slot input and assert byte-identical request construction across runs.
- **Boundary cases that must be covered:** zero directory matches; multiple matches (clarify); `acara_sml_id` absent from directory (`bad_request`, repairable); directory-valid record missing geography (`unanswerable`); SA2 market must NOT request a radius (O-8); distance market MUST require radius; `peer_filters`/`segment_filters` with only defaults present (clarify); empty user metric list → omit `metrics`; a metric synonym that is not in the static-closed vocabulary → `bad_request` vs clarification.
- **Verbatim-limitations and no-grade invariants (ADR-009/ADR-014).** If the planner participates in request/response assembly, tests must confirm it does not route preserved fields (`limitations`, `confidence.grade`) through the model or assign a grade.
- **Over-defaulting regression.** A grader/test should fail if the planner writes any DEFAULTABLE key into the outbound `request`, protecting the `golden_cases.json` "omit defaultable" invariant.



## Falsifiable questions for planning

1. Which single artifact does the planner read to decide REQUIRED vs MATERIAL vs DEFAULTABLE — the pinned registry `input_policy`, the per-question `x-poc` block, `_index.json`, or the `settings.MATERIAL_INPUTS` shim? (Determinism and O-1/O-8 exposure hinge on this.)
2. When the emitter returns `bad_request` for a request the planner itself constructed, does the outcome become a harness failure or an `Unsupported` refusal (ADR-014 currently the latter)? What distinguishes a planner defect from a user-driven unanswerable in code?
3. Does the change introduce or remove a hand-maintained conditional-materiality table for `distance_km`, and does it flip the O-8 `xfail` in `test_agent_loop.py`? Is O-8 updated accordingly?
4. Does "construct exact evidence requests" ever populate defaultable fields in `request`, and if so how do the `answer/*` golden cases (which omit them) still pass?
5. Is metric normalization owned by the planner, the prompt (`rules.md`), or both — and what test guards against divergence?
6. For school resolution, are zero-match, multi-match, absent-ID, and missing-geography cases each mapped to distinct, tested outcomes without any name-matching or `School_No` crosswalk?
7. Is planner determinism tested in isolation with fixed intent input, independent of the model's non-deterministic question selection?
8. Does any planner behaviour depend on preflight/`result.data` fields that `decisions.md` O-6 flags as still invented in the stub, such that offline tests would not exercise the live path?
