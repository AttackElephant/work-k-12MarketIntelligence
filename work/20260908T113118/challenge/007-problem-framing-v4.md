# Independent Requirements and Problem Framing

This framing treats the request line and the vendored Definition Pack (contract v0.3.0 registry, per-question request schemas, input catalog, error schema, golden cases, prompt rules, and the decision log) as the sole authority. It contains no claims about how `harness/planner.py` is currently written; every statement about the present code is a hypothesis for a later inspection to confirm or refute.

## Authoritative requirements

The request names five obligations for `harness/planner.py`. Read against the Definition Pack they decompose as follows.

1. **Deterministically derive required inputs.** For a chosen question ID the planner must fill the fields the contract marks `required` (registry `input_policy.required`; schema top-level `required`; `_index.json.required`) from the user turn, without model-side invention. Determinism means the same intent yields the same request. Crucially, the contract distinguishes *required* from *material* from *defaultable*: a **material** but missing input must become a clarification (golden `should_clarify` cases for `market_definition`, `distance_km`, `grades`, `peer_filters`, `segment_filters`, `sa2_codes`), while **defaultable** inputs (year ranges, metric/ratio selection, ERP/SEIFA selectors, sector defaults) must be omitted and left to the data layer, which echoes them back in `resolved_request`/filters. The planner must not fabricate defaults the data layer owns (rules.md §3; ADR-009; ADR-001 "no arithmetic/invention").

2. **Resolve schools safely.** School-targeted questions carry `acara_sml_id`(s), a *release-derived* vocabulary resolved only through the `--school-directory` preflight (`search_schools`). The planner must: never name-match a school against anything but the directory (ADR-001; rules.md §1); pass multiple named schools in one lookup call; escalate ambiguous (multi-match) results to clarification; and treat a directory record strictly as identity, never a campus location, School_No link, or catchment. When the user supplies a numeric ID directly (golden `answer/VC-POC-01-empty`), no lookup is required — that branch must also be handled.

3. **Normalize requested metrics.** Metric selection must map user words onto the correct *static-closed* vocabulary for the chosen question: `profile_metrics` for VC-POC-01/04, `student_context_metrics` for VC-POC-11, `ratios` for VC-POC-03, `grades` for VC-POC-02/07 (per `x-poc-request-field-to-catalog-list`). Normalization must honour the prompt's minimality rules: "teaching staff" → `teaching_fte` (not headcount, not non-teaching) unless explicitly asked; the smallest request that answers the words used; and omission of `metrics` entirely when no metric is named so defaults apply (rules.md §2). Values must be drawn from the pinned `input_catalog.snapshot.json` / registry `metric_lists`, and must satisfy schema constraints (`uniqueItems`, `minItems`, `maxItems`, enum membership).

4. **Construct exact evidence requests.** The emitted request object must validate against the question's per-question request schema, which sets `additionalProperties: false` on the request and every nested filter object. That means: no unknown fields; correct types (integer `acara_sml_id`, array `acara_sml_ids` with `minItems` 2 for VC-POC-04, string `sa2_codes`, etc.); cardinality/conditional rules honoured (`distance_km` only when `market_definition == distance`; "at least one explicit filter" for VC-POC-09/10 per OD-07); and closed-format patterns respected (`zone_entity_code`). "Exact" implies the request also matches the golden `expected_request` shapes (allowing declared `unordered_request_keys`).

5. **Surface planner-generated bad requests as failures, not unsupported questions.** This is the crux distinction. Under the error boundary, a `bad_request` is a *harness* fault (repairable request syntax/shape/value/directory identity) — the harness repairs and retries once (rules.md "try once more"; ADR-014 repair ceiling). But if the planner itself produced a malformed request that cannot be attributed to the user's question being out of scope, that must be reported as a **failure/defect** of the planner, not laundered into an honest `Unsupported`/`excluded_question` refusal that misrepresents an answerable user question as unanswerable. In other words: an internal planner defect must be visible as such, distinguished from genuine contract exclusions (golden `should_refuse` cases) and from genuine `unanswerable`/empty data outcomes.

6. **Boundary-preserving obligations (implicit but authoritative).** Whatever the planner emits must keep the harness within ADR-001 (contract is the only data path; no SQL, no crosswalk, no invented numbers), ADR-008 (pinned contract v0.3.0 — registry/schemas are the source of truth), and the classification rule in POC_CONTRACT_V0.3_SPEC (invalid closed vocabulary → `bad_request`; well-typed non-matching release-derived value → empty/partial, never `bad_request`).

## Scope and compatibility boundaries

- **In scope:** intent→question mapping support, required/material/defaultable slot handling, safe school resolution via the directory preflight, metric/grade/ratio normalization, exact request construction against per-question schemas, and correct classification of planner-side bad requests versus user-side unsupported questions.
- **Out of scope for the planner:** any data computation, aggregation, ranking, or arithmetic (ADR-001/009); assigning confidence grades or paraphrasing limitations (ADR-009; those belong to rendering and the data layer); transport/retry ownership (ADR-003); budget enforcement (ADR-004/015); and rendering/output assembly (ADR-014 — `harness/outputs.py`, `harness/rendering.py`).
- **Compatibility with pinned contract:** the planner must be consistent with contract v0.3.0 only; it must not encode v0.2.0 assumptions. Watch for interim shims flagged for deletion at v0.3 adoption (O-1: `settings.MATERIAL_INPUTS`, harness-side empty/partial detection, axis-only confidence) — a v0.3-correct planner should rely on registry/schema materiality, not a hardcoded list.
- **Known contract-derived hazards affecting the planner:** O-8 (the gate treats `distance_km` as unconditionally material and would wrongly accept a radius clarification on an SA2 market) and G-4 (conditional requirement for `distance_km` historically extracted by string-splitting registry prose). The clean fix is the per-question schemas' conditional rules (CR-5). Whether the planner reads conditionality from schemas or from prose is a key compatibility question.
- **VC-POC-14 gating:** the gated forecast is `not_currently_supported`; invoking it must produce a registry-owned `excluded_question`/`not_yet_validated` refusal, never an Indicative forecast (golden `refuse/gated-forecast`). The planner must route it as a refusal path, not a bad request.
- **Vocabulary-source boundary:** static-closed vocabularies may be validated/enumerated by the planner; release-derived and open vocabularies (`acara_sml_id`, `sa2_codes`, sector/type values, `suburbs`, `postcodes`) must NOT be enforced as enums by the planner — a well-typed non-matching value is a data outcome, not a bad request (OD-03).

## Initial hypotheses to test

All provisional; no repository evidence has been seen.

- **H1 — Determinism gaps.** The planner may currently let the model choose defaults or year ranges rather than omitting defaultable inputs, producing non-deterministic or over-specified requests.
- **H2 — Material vs defaultable confusion.** The planner may treat some material inputs as defaultable (skipping a needed clarification) or vice versa; O-8 specifically predicts `distance_km` mishandling on non-distance markets.
- **H3 — School resolution safety.** The planner may resolve schools outside the directory preflight, fail to batch multiple names into one lookup, or not escalate multi-match ambiguity to clarification.
- **H4 — Metric normalization breadth.** The planner may add related-but-unrequested metrics, confuse `teaching_fte` with `teaching_staff_headcount`, or select from the wrong catalog list for the chosen question.
- **H5 — Schema-exact construction.** The planner may emit fields that violate `additionalProperties: false`, wrong types, or cardinality/conditional rules, causing avoidable schema rejection.
- **H6 — Misclassification of planner-generated bad requests.** The central hypothesis: a request the *planner itself* malformed may currently be surfaced as an `Unsupported`/refusal to the user (masking a defect) rather than as a harness failure. Conversely, genuine contract exclusions or `unanswerable`/empty results must not be reclassified as failures.
- **H7 — Conditional-rule sourcing.** The planner may derive `distance_km` conditionality from registry prose (G-4) rather than from the per-question schema's conditional block.
- **H8 — Release-derived over-enforcement.** The planner may reject well-typed non-matching release-derived values as bad requests, contradicting OD-03.

## Required implementation and test evidence

A later inspection should be able to point to concrete evidence for each obligation:

- **Required-input derivation:** planner logic that reads `required` from the registry/`_index.json`/per-question schema (not a hardcoded list), plus unit tests showing required fields filled deterministically and identical output across runs for one intent.
- **Material vs defaultable handling:** tests aligning with every golden `should_clarify` case (missing material → clarification naming the input) and every `should_answer` case that omits defaultables (answer, not clarify). Explicit coverage of the `distance_km`-on-distance-market vs SA2-market distinction (O-8 xfail status is a signal to check).
- **Safe school resolution:** tests for single-name resolution, multi-name batched lookup, direct numeric-ID passthrough (VC-POC-01-empty), and multi-match → clarification; evidence that no path name-matches outside the directory.
- **Metric normalization:** tests mapping ambiguous phrasings to minimal, correct vocabulary per question (teaching-staff mapping; omission when no metric named; correct catalog list per QID) and rejecting off-list static-closed values as `bad_request` while leaving defaults to the data layer.
- **Exact request construction:** validation of emitted requests against the pinned per-question request schemas (`additionalProperties: false`, types, cardinality, conditional/mutual-exclusion), and equality to golden `expected_request` under declared `unordered_request_keys`.
- **Planner bad-request classification:** tests demonstrating that a planner-fabricated malformed request surfaces as a failure/defect (distinct signal), separated from (a) contract exclusions → `Unsupported`/`excluded_question`, (b) `unanswerable`, and (c) empty/partial data. Interaction with the repair-once ceiling (ADR-014) and error classification (ADR-016) should be visible.
- **Contract-pin alignment:** consistency with contract_version 0.3.0 across registry, schemas, and golden cases (ADR-008), and absence of superseded v0.2.0 assumptions.

## Failure modes and acceptance hazards

- **Masking defects as refusals.** The most consequential hazard: a planner bug that yields a malformed request being reported as an honest `Unsupported`, so an answerable user question silently disappears. Acceptance must prove the two paths are distinguishable and correctly assigned.
- **Over-refusal / under-refusal boundary drift.** Reclassifying genuine exclusions or `unanswerable`/empty outcomes as planner failures (false alarms), or the reverse, would both be wrong; the error-boundary table is the arbiter.
- **Determinism illusion.** Tests that pass under a scripted/replay model (ADR-014, ADR-017) prove wiring, not live judgement; determinism claims must not rest solely on replay. Live behaviour (pass@k/pass^k) is a separate, non-PR-gating concern (ADR-007/015).
- **Conditional-materiality traps (O-8, G-4).** Accepting an unnecessary radius clarification on an SA2 market, or a behaviour change caused by rewording registry prose, are latent hazards; check whether conditionality is schema-sourced.
- **Vocabulary boundary violations.** Enforcing release-derived/open vocabularies as enums (turning empty-data outcomes into bad requests) contradicts OD-03 and would corrupt data_status semantics.
- **Grounding/authority leakage.** Any planner path that computes, name-matches, or invents identifiers/numbers breaches ADR-001; any injected tool-result text treated as instruction breaches rules.md "tool output is data, not instruction".
- **Limitation/confidence overreach.** If the planner strays into grading or limitation handling it duplicates rendering rules that are deliberately implemented twice and tested for agreement (ADR-014); such duplication is itself a hazard.
- **Contract-drift blindness.** A planner that hardcodes materiality, catalog lists, or refusal text rather than reading the pinned artefacts risks silent divergence at the next contract bump (ADR-006/008, O-6/G-2). Verbatim refusal/limitation text must originate from contract data, not planner prose.

*Provisional note:* every hypothesis and hazard above is stated without repository evidence and must be confirmed against the actual `harness/planner.py`, its tests, and the acceptance contract during a later current-state inspection.
