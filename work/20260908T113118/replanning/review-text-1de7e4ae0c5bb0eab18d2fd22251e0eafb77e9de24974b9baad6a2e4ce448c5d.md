# Independent Plan Review

## Approach challenges

**A1 — The whole plan is wrong if `planner.py` is not the production path.**
The plan (`planning/001-plan.md`, "Bounded objective" and "Do not alter the legacy agent-tool repair loop") assumes the deterministic pipeline in `harness/planner.py` is what ships and that the PydanticAI `agent.iter()` tool loop is "legacy." Repository evidence points the other way: `docs/decisions.md` ADR‑014/ADR‑015 describe `ask()` driving `agent.iter()` with `fetch_evidence` repair (`retries=MAX_REPAIR_ATTEMPTS`) as the live control path, and ADR‑018/ADR‑019 wire the shipping `claude_account` provider through that Pydantic‑AI loop. The problem analysis records this as unresolved (Q7, "Which execution path is production … is unconfirmed"). *Consequence:* if the agent loop ships, then fixing `planner.py` satisfies the tests but leaves request requirement (5) unmet on the code customers actually hit. *Disproved if:* `run.py`/`harness.agent` wiring shows `plan_and_execute()` is the default dispatch for the default provider, or the agent loop is dead/unreachable code.

**A2 — Collapsing every `bad_request` into `TerminalError` is wrong if any `bad_request` origin is legitimately user-facing.** The plan ("Change the `bad_request` branch to raise `TerminalError`") and the contract (`failure_behaviour`: "The emitter returns bad_request after deterministic planning → raise TerminalError") treat *all* `bad_request` as operational failure. But `POC_CONTRACT_V0.3_SPEC.md` ("Error boundary") classifies a directory‑absent `acara_sml_id` as `bad_request` because "the harness violated the selector obligation" — repairable, not internal. A user who types an explicit numeric ID absent from the directory would, under the real emitter, produce `bad_request`, which the plan now turns into an operational crash instead of a clarify/refuse. The problem analysis (Q2, "three `bad_request` dispositions must be separated") flags exactly this. *Consequence:* user-caused input errors become `TerminalError` operational stops. *Disproved if:* the planner separates planner-shape defect (failure) from directory-absent explicit ID (user-facing) from release-derived non-match (empty/partial), each with its own test.

**A3 — "Deterministic derivation" is only as deterministic as the intent model.** The plan distrusts `StructuredIntent.missing_material_inputs` but still builds requests from `intent.filters` and `intent.requested_metrics` (plan: "derive all other missing material fields from the assembled filters"; "Normalize metric labels … preserving already-canonical values"). Those slots are themselves LLM-produced (per 005, "Stage 1 supplies the slots the planner trusts"). *Consequence:* requirement (1)/(3) determinism is bounded by intent extraction; a metric the model drops or a filter it invents cannot be recovered/rejected by "derivation." *Disproved if:* the planner re-derives selectors from the raw user text rather than from model-populated `StructuredIntent` fields, or `intent.py` is shown to be rule-based rather than model-driven.

## Approach challenges

1. **"Every planner `bad_request` is a harness defect → `TerminalError`" is contradicted by the contract the plan itself cites.** `harness/planner.py` today maps `bad_request → Unsupported(out_of_scope)` and the plan replaces this with an unconditional `TerminalError` (`error-boundary-refinement`). 3. **"Exactly one directory record per mention" can convert answerable questions into clarifications.** `poc_school_directory.v0.3.0.schema.json` `school_search` is a substring/name search; a common name can legitimately return several records. Current code takes `resolved[0]`; the plan mandates clarify on ≠1 (`safe-school-resolution`). *Consequence:* golden `answer/VC-POC-01` etc. could regress to clarifications if their phrasings return >1 record. *Disproof:* evidence that each golden answer phrasing yields exactly one directory record, **or** that golden answer cases are replayed through the legacy loop rather than the planner. *Missing evidence:* no live/fixture directory sample and no `run.py`/`test_agent_loop.py` in this turn to establish which path golden replay drives (ADR-016 warns offline completeness is silence about the live path).

4. **Runtime `--input-catalog` load undercuts "deterministic."** The plan loads the catalog through the client "when requested metric normalization is needed." But `profile_metrics`/`student_context_metrics`/`ratios` are `static_closed` (`poc_input_catalog…schema.json` `x-poc-static-vs-release-derived`) and already pinned in `prompts/input_catalog.snapshot.json` and the registry. *Consequence:* a per-run subprocess call to the data-project emitter for values that are static introduces a data-project dependency and non-determinism into a "deterministic Stage 2." *Disproof:* the planner reads static vocabularies from `contract`/the pinned snapshot rather than a runtime emitter call.
